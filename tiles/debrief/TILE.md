# debrief

After the work lands — or fails — extract what the next briefing
should know. This is the learning loop the tiles are built on:
trial, debrief, tile updated.

## The mad-lib

> **What was asked:** ___
>
> **What happened:** ___ (one paragraph, no blame)
>
> **What was lost in translation:** ___ (where the brief and the
>  result diverged — be specific)
>
> **What survived:** ___ (what the brief got right)
>
> **What changes:** ___ (one concrete change to the brief, the
>  tile, or the procedure — not three)

## Rules

- Write it while it's fresh. A debrief from memory a week later
  is a story, not a debrief.
- One concrete change. If everything needs changing, the tile was
  wrong, not the run — rewrite the tile.
- File it where the next person briefing this task will find it.
  A debrief nobody reads is a diary entry.
- No blame. The question is always "what in the procedure
  allowed this," never "who."

## What this won't do

- It won't fix a broken tile. It tells you the tile is broken.
- It won't help if nobody reads it. The value is in the next
  brief, not in this document.
